# Ophis OTC Integration Plan

**Status:** Planning only. No contract, frontend, or indexer deployment is authorized by this document.

**Goal:** Add a fixed-price, peer-to-peer OTC experience under the Ophis brand, initially on Ethereum, using the existing immutable execution contract rather than deploying a second Ethereum order book.

## Confirmed baseline (2026-08-18)

- Upstream source: `ETHCF/swapboard`, commit `7042b1b82defec0eecc4fce668df0fa815e8cc47`.
- Ethereum contract: `0x000000fF3D7A2d373615141d7489Ca66683DbecF`.
- Expected runtime code hash: `0x8d9ad2a9d3b3d47aaa832ecc21de8775509764409ab07cdf097640396d10eda1`.
- Constructor WETH: `0xC02aaA39b223FE8D0A0e5C4F27eAD9083C756Cc2`.
- The deployed contract is verified, immutable, non-upgradeable, has no owner, and charges no protocol fee.
- The execution contract supports atomic full fills, cancellation, native ETH wrappers, and a taker-supplied fill deadline. It does not support partial fills or maker-side order expiration.
- The public Goldsky subgraph is useful for discovery, but contract state is the only settlement authority.
- Source is AGPL-3.0. Ophis will implement its own UI and adapter against the public ABI. Any copied or modified source must preserve the license and receive legal review.

## Release scope

### Ethereum v1

- Ophis `/otc` route with browse, filter, create, fill, cancel, and wallet-specific views.
- Reuse the live Ethereum contract and its existing liquidity/order history.
- Exact-input, all-or-nothing ERC-20 orders first; native ETH wrappers follow after the ERC-20 path passes review.
- Ophis token-policy enforcement on both order legs. Unknown or unsupported assets may be shown read-only but cannot be created or filled through Ophis.
- No copied upstream UI, no third-party branding in the product, no partial fills, no cross-chain orders, and no new execution contract.

### Explicitly out of scope for v1

- Other-chain deployments, maker-enforced expiry, private/RFQ orders, order matching, partial fills, protocol fees, custodial recovery, or an admin pause.
- Claims that orders expire: the current contract leaves orders active until filled or cancelled.

## Required implementation controls

- Pin `chainId`, contract address, ABI selectors, WETH address, and runtime code hash. Never follow an address returned by remote configuration.
- Treat the subgraph as an index only. Before every wallet interaction, read `getOrder`, confirm the order is active and unchanged, and simulate the exact call against the latest block.
- Use a short, nonzero taker deadline. Show stale-order age and price deviation prominently; maker expiry cannot be enforced by this contract.
- Introduce an escrow-specific token-policy profile. Reject rebasing, fee-on-transfer, callback-heavy, unknown, and deceptive tokens on both legs. Exact address allowlisting is the v1 default.
- Flag blacklistable or upgradeable assets as an escrow lock risk. Enabling one requires a documented product/security exception.
- Use exact approvals only. Atomic approve-plus-create is available only when the wallet capability parser validates batching; otherwise show the two required transactions clearly.
- Never label OTC approvals or fills as gas-free. The existing execution contract has no permit entry point, and all on-chain operations consume gas.
- Resolve token names, decimals, symbols, and logos from Ophis-curated metadata. Never render arbitrary token metadata as HTML.
- Keep order creation and settlement analytics free of sensitive wallet-provider data. Record chain, selector, order ID, simulation result, receipt, and index lag.

## Test and review matrix

- Unit: ABI encoding, deadlines, amount conversion, token policy, stale-state rejection, and name/metadata rendering.
- Contract adapter: runtime hash, WETH, order decoding, selector allowlist, transaction value, recipient behavior, and revert normalization.
- Mainnet fork: create/fill/cancel ERC-20; all ETH wrapper variants; competing fills; cancellation race; expired taker deadline; paused, rebasing, fee-on-transfer, and false-return tokens.
- Indexer: reorg handling, deployment-block backfill, deduplication, pagination, lag detection, and direct-contract reconciliation.
- E2E: injected wallet, Safe, valid and malformed atomic capabilities, rejected token policy, network switch, rejected signature, reverted transaction, and recovery after stale subgraph data.
- Differential review: compare the pinned deployed contract with both published audit commits and review every semantic delta from those commits.

## RPC and indexing decision

A specific paid RPC is **not required** for Ethereum v1. Wallet writes use the connected wallet provider; contract reads and simulations can use Ophis's existing provider abstraction with a public-RPC fallback. On 2026-08-18, a keyless public Ethereum RPC returned the pinned bytecode, WETH address, and live order counter successfully.

Do not copy the upstream frontend's embedded Alchemy URL. For discovery, the existing public Goldsky endpoint can support shadow mode and early canary use. It remains an upstream-operated dependency, so production must add an Ophis-controlled event mirror or at least a second index source plus direct on-chain reconciliation. A paid provider may improve rate limits and reliability later, but it is an operational choice, not a protocol requirement.

## Other chains

Each additional chain is a separate project and separate liquidity domain. It requires canonical wrapped-native-token verification, EIP-1153/Cancun support, explorer verification, deployment-block indexing, runtime-hash pinning, fork tests, and a fresh security sign-off. Chains with native-token/ERC-20 aliasing or incompatible transient storage are rejected. No other-chain deployment occurs as part of Ethereum v1.

## Principal risks and mitigations

| Risk | Mitigation |
|---|---|
| Malicious payment token lets a taker receive escrow without real payment | Strict two-leg allowlist; no arbitrary-token execution |
| Rebase, pause, or blacklist locks escrow | Escrow-specific deny policy, warnings, documented exceptions, and no unsupported creation |
| Stale maker order becomes economically unfavorable | Age/deviation warnings, cancellation reminders, and clear disclosure that only cancellation ends the order |
| Stale or manipulated index data | Re-read and simulate on-chain immediately before signing; fail closed on mismatch |
| Immutable contract incident | Feature flag hides Ophis execution immediately; publish incident notice; contract and existing orders cannot be paused by Ophis |
| Upstream endpoint disappears or rate-limits | Ophis event mirror, second source, cached pages, and degraded read-only mode |
| Licensing or provenance confusion | Clean Ophis UI/adapter, preserve upstream attribution in technical docs, legal review before copying source |

## Deployment authorization

No deployment or production feature enablement occurs until the final commit, contract manifest, monitoring plan, and rollback runbook are green; Trail of Bits, Verity, and Pashov reviews are approved; and the user gives explicit deployment approval.
