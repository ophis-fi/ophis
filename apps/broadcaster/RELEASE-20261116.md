# Native prepaid broadcaster release — 16 November 2026

This candidate extends the existing Ethereum/BNB native-prepayment service to public Arbitrum admission. Base remains pilot-only pending successful conditional inclusion; Polygon is deferred. Enabling Arbitrum does not advertise it as MEV-protected.

## Preserve customer liabilities

Use the existing operator, state directories, requests database, protected-transaction database and credit identity. Before activation, inspect the ledger read-only and set `OPHIS_BROADCASTER_CREDIT_LEDGER_ID` to that existing nonzero ID. Keep the pin in normal service and recovery configuration. A missing or mismatched ledger must stop signing; it is not a reason to initialize replacement state.

For pilot-to-public transition, remove only the pilot account, withdrawal recipient, prepaid pilot owner and pilot-only ledger binding. Set admission to `public` and payment mode to `public-native`; retain the independent expected ledger ID above. Preserve the used pilot marker and every balance, hold, original signature, cancellation and nonce row. No credit conversion or database migration is needed. Disabled initialization is only for a deliberately new ledger, never a replacement for lost customer records.

The Arbitrum candidate retains the reviewed 0.1 gwei gas-price ceiling, 0.001 ETH transaction-cost ceiling, 0.001 ETH rolling daily budget, 0.001 ETH reserve and 15% margin. The browser pins matching price/cost limits and operator identity. Customer credit covers the validated worst-case operation cost and margin before signing. Included failures and cancellations charge actual gas plus margin; unused credit remains a liability. Public credit funding has no PPOI standby period, but chain finality still applies.

## Release checks

1. Freeze source, lockfiles, generated guard artifact and production bundle hashes. Match the repository default branch and review any new changes before release.
2. Run broadcaster/client tests, TypeScript checks, guard artifact reproduction and contract tests. Review accounting, owner authorization, unknown outcomes, repeated admission, refunds and restored-state refusal. Run Semgrep, CodeQL, Gitleaks and Trivy on their stated source/image scopes; record actual findings and triage rather than claiming every scanner is empty.
3. Build the broadcaster from the allowlisted Docker context. Verify its bundle label, unprivileged UID, read-only runtime, absence of package managers, exact APT fixes and installed dependencies. Retain the old image for rollback, but never roll customer journals back to an earlier snapshot.
4. Preserve an encrypted, consistent backup under the established operator procedure. Verify no pending signed request or unsettled credit is lost in the service transition. Stage only the Arbitrum broadcaster project; do not modify Ethereum nodes, mev-boost, validator services, other broadcaster state, or billing.
5. Install the reviewed release, verify state identity/resource limits/messaging, and let the owner unlock locally with the existing helper. Verify readiness, discovery and ledger continuity. Do not spend customer funds, erase a used pilot marker or replay earlier one-off test approvals as a health check.

## Recovery and monitoring

Monitor gas backing, remaining daily budget, pending operator nonces, unsettled holds, failed synchronization, Waku connectivity and disk capacity. A Docker liveness check is not proof of readiness. The existing monitor command may alert while a used pilot is deliberately closed; this must not be masked by deleting its marker. A restart loses the in-memory gas key and requires owner unlock.

On a failed deployment, preserve the complete current state and all signed bytes. Any restored-state marker deliberately blocks signing until operator reconciliation. Do not restore an older financial database merely to roll application code back. Customer balance queries/recovery must remain bound to the same chain, operator and ledger.

## Base release hold

Base's official conditional route has acknowledged test transactions without inclusion. Format, predicate, expiry and cost-ceiling tests do not establish delivery. There is no unconditional RPC fallback. The reproduced cancellation crash-recovery issue is fixed, but activating Base still requires a diagnosed route and fresh bounded owner-approved inclusion/exclusion acceptance. Prior single-transaction approvals are consumed.

## Assurance boundaries

The unchanged Solidity guard is tied to its prior audit hashes and fresh compiler/Slither/Foundry checks. The checked Verity model covers admission, nonce progression and rollback under explicit external-call assumptions; it is not bytecode or EIP-7702 equivalence. Static analysis and dependency reachability review cannot establish a live provider's inclusion guarantees or protect a spending key from an administrator/host compromise.
