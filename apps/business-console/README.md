# Ophis Business console

Production on pro.ophis.fi (2026-11-17), all on Cloudflare's Free plans: nothing in it can be billed (no R2). Passkey sign-in, enrolment of members (each new passkey confirmed by a colleague), roles with two-person approval and the audit log, wallets with the recovery wallet, last-Owner recovery, Support, and registration by invitation with the operator's review. Design, schema, routes and invariants: `ARCHITECTURE.md`.
Production runbook (hosts, secrets, updates, the monthly OFAC load, a new client): `OPERATIONS.md`. Deploys run in CI on merge to main (`.github/workflows/business-console-deploy.yml`); never deploy from a laptop. Its token cannot touch D1: a PR that adds a migration is applied by hand before its merge (`npx wrangler d1 migrations apply ophis-business --remote --env production`). The first deploy (2026-11-17) ran from the operator's Mac: it created the three custom domains, which the CI token cannot.

Needs Node 22.18 or later and Google Chrome. Run everything from this folder, with pnpm as `npx -y pnpm@10.34.9`.

```sh
npx -y pnpm@10.34.9 install --ignore-workspace   # the flag is required: without it pnpm installs the root workspace
npx -y pnpm@10.34.9 migrate     # creates or updates the local D1 database (.wrangler/); run it again after pulling (now up to 0018, which keeps who gave an order's signing link and the fee the orderbook reports; 0017 adds the orders of the desk; 0016 records how a wallet's link was proved; 0015 adds the people an application names and the seat's mark "approved by Ophis"; 0014 closed the links the company sign-in left open and dropped its columns, removed on 2026-11-13; 0013 dropped two unused columns of the enrolment links; 0012 gained two triggers and the column made_at on 2026-11-13: a local database made before that must be rebuilt: delete .wrangler/state, then migrate and seed again). If it fails with "duplicate column name" (0005_onboarding.sql was renamed 0006): stop dev, delete .wrangler/state, migrate and seed again
npx -y pnpm@10.34.9 seed        # one organisation (domain northwind.example), one Owner seat; prints a one-time enrolment link (10 minutes)
npx -y pnpm@10.34.9 dev         # builds the console and the signing page, and serves both with the Worker: console http://localhost:8787, signing page http://127.0.0.1:8787/sign/. Also starts the local stand-ins (scripts/stubs.mjs): the rebate indexer (8793), the OFAC list file (8794), and the orderbooks with the chains' endpoints for Overview's balances (8795)
npx -y pnpm@10.34.9 seed -- --demo   # LOCAL ENVIRONMENT ONLY: the organisation is an institution with two linked wallets that no signature proved, "Demo wallet" (the first public test key of anvil) and "Demo Safe" (a Safe, random address); the command refuses any environment but "local"
npx -y pnpm@10.34.9 seed -- --live   # partner figures, LOCAL ENVIRONMENT ONLY: the organisation is a partner with one linked "Demo wallet" at the partner address of the indexer's contract file, so Overview shows the stand-in's figures
npx -y pnpm@10.34.9 activate    # first Owner only: local stand-in for the activation by the recovery wallet (milestone 5)
npx -y pnpm@10.34.9 skip        # local stand-in for the passing of time: every wait that runs is over (recovery wallet 72 h, recovery request, 24 h after a cancel)
npx -y pnpm@10.34.9 operator list        # milestone 5: the operator's command (also: invite, decide, screen, addresses, sync, freeze, unfreeze, items, get); needs "dev" running; with --production it goes to operator.ophis.fi
```

`seed` writes `.dev.vars` when it is missing and adds what it lacks (the challenge key, the operator's token, `INDEXER_URL` with `INDEXER_TOKEN` for the local stand-in of the rebate indexer, `SANCTIONS_URL`, `ORDERBOOK_URL`, and `RPC_URL` for the endpoints Overview reads balances on). It is git-ignored: never commit or print it. A file made before 2026-11-13 may still hold `MICROSOFT_CLIENT_SECRET` and `GOOGLE_CLIENT_SECRET`: nothing reads them, and the two lines can go.

## The quick look: one command, no security key
`npx -y pnpm@10.34.9 tour` (from this folder) starts the local server on a throwaway database and opens three Chrome windows, each already signed in with a test key: the Owner of a partner (Overview, with the figures of the local stand-in), the Owner of an institution (Desk; its Overview shows the test balances of its two wallets) and its Approver (Organisation, Approvals). Prepare an order in window 2 and approve it in window 3. Before it hands over, the tour runs the operator's own command: `sync` reads the test list file of the local stand-in, and `screen` records a clear sanctions screening for both organisations with the test files of `tests/fixtures/`, so Compliance shows them in windows 1 and 2. Passkey checks answer by themselves in these three tabs only: a new tab has no key. Ctrl+C in the terminal, or quitting that Chrome, stops everything. Port 8787 must be free. `TOUR_CHECK=1` runs it without a window: the Owner sends an order, the Approver approves it, Compliance shows the screening, and it ends (`TOUR_CHECK=window`: the same with the windows).

## A tester gets in, step by step
Everything starts at http://localhost:8787 (the console). Use Chrome. Each person needs a security key of their own, or a Chrome virtual authenticator per browser profile (DevTools, More tools, WebAuthn: ctap2, usb, resident keys, user verification).
1. Once: `install`, `migrate`, then `seed`. Keep the link it prints (10 minutes).
2. `dev`, and leave it running. Open http://localhost:8787 : the sign-in page, with the footer line.
3. Open the printed link. Create the passkey. In a second terminal run `activate` (it stands in for the first Owner's activation). Go to http://localhost:8787 and press "Sign in with a passkey".
4. Organisation, My passkeys, "Add a passkey" (a second key, optional: one passkey is enough).
5. "Invite member": a name and a role. Copy the link.
6. In another browser profile open the link and press "Create passkey".
7. Back as the Owner: reload. Under "Waiting for confirmation" the card names the member, the role and when the passkey was created. Check with the member, by a channel you both trust, that they created it, then press "Confirm with passkey". A key role needs a second key-role member too, or waits 72 hours if there is none (`activate` stands in for that wait).
8. The new member signs in at http://localhost:8787 with the passkey.
9. A new organisation from scratch (registration): `operator invite` prints an application code; open http://localhost:8787/apply and follow "Onboarding" below.

Then, in the app (each person needs their own security key, or a Chrome virtual authenticator per browser profile):
1. Organisation, My passkeys, "Add a passkey". An Owner needs two hardware keys before anything else works.
2. "Invite member" gives a one-time link: 10 minutes for key roles, 24 hours for Trader and Viewer. The member opens it on their own device and creates a passkey. Any company works this way, whatever its email domain and its systems.
3. Under "Waiting for confirmation" the inviter checks with the member, by a channel both trust, that they created the passkey, and confirms with a passkey within 60 minutes. The console cannot tell who created the passkey: that rests on the channel the inviter sent the link by and on this check. Key roles need a second key-role member too. Only an organisation that has had no other key-role member in the last 30 days waits 72 hours instead (locally, `activate` stands in for that wait). A person Ophis approved with the organisation needs neither at their first enrolment (Onboarding, step 5).
4. "Re-enrol" does the same for a member who lost every passkey. The old passkeys are suspended: for 24 or 72 hours one of them can still sign in to a page with one action, "Stop this replacement".
5. A stop freezes the seat. An Owner or Admin can also freeze a seat at once: Members and roles, "Manage", "Freeze seat". A frozen member who signs in sees who froze the seat and when; a replaced passkey can still stop its replacement on a frozen seat. A member's last passkey is never revoked.
6. Unfreezing a seat, removing a member, changing a role and changing the passkey rule for key roles take two people: one asks ("Manage", or the passkey rule section), a different member with a key role approves under "Approvals" after a passkey check. Each button is preceded by what it will do.
7. Compliance (Owner, Compliance officer, Viewer): the audit log in plain words with both hashes per row, "Chain verified" computed by the server with the rows it verified (each load checks the new rows and re-checks older ones in turn), and "Export CSV" (fetched in pages, saved as one file).
8. Two passkeys of one seat need different names. If the local database already holds two with the same name, `migrate` fails: delete `.wrangler/` and seed again.
9. Wallets (Organisation, Wallets): an Owner or Admin uses "Link a wallet" and gets a signing link, valid 7 days. Nothing is stored yet. The link opens the signing page on its own address (`http://127.0.0.1:8787/sign/` locally), in the browser that holds the wallet. The wallet signs one typed message that names the organisation. A wallet with one key, or a custodian's browser extension, signs through the browser. A Safe signs inside the Safe interface (below).
10. With colleagues in key roles the link then waits under "Approvals" for a different member. An organisation with a single key-role member links at once. "Manage" on a wallet: "Unlink" (one person; never the recovery wallet), "Set as recovery wallet" (an Owner asks, a second person approves, in force 72 hours later), "Cancel change" (any Owner, during the 72 hours).
11. Organisation, at the end of the page, for an Owner: "Recovery readiness" says Ready, At risk with the next step, or Not recoverable. A Safe that is the recovery wallet is read on the chain at that moment: green needs a genuine Safe (official proxy code, singleton and fallback handler), a threshold of 2 or more, no module, and the owners it had when it was approved. A contract that only answers like a Safe is stored as a single key. Below it: the recovery sheet, with "Print the recovery sheet".
12. Last-Owner recovery, when no Owner can sign in. Open http://localhost:8787/recover (no sign-in), enter the organisation id from the recovery sheet and create a passkey on a new security key. The page shows a signing link: give it to the signers of the recovery wallet by a channel they trust. They open it on the signing page, compare the organisation id with the recovery sheet, and sign. Nothing else shows them that the passkey in the link is yours. Then the request waits 72 hours (`skip` locally). Every member sees a banner at sign-in: an Owner can cancel after a passkey check, an Admin, Approver or Compliance officer can add 72 hours once, and the recovery wallet can cancel by signing (the form on /recover, with the request number from the banner). After the wait, "Continue with the new passkey" on /recover makes the requester an Owner. For 7 days the organisation is in quarantine and a replaced Owner passkey, used at sign-in, can stop the recovery. The next request can start 24 hours after a cancel, and not while a completed recovery can still be stopped (7 days, or until it is stopped).
13. An override ("Override the Owners" on /recover) works only for a green recovery wallet, within 30 days of an Owner cancelling or stopping a recovery. No Owner can cancel or stop it: only the recovery wallet can cancel it, by signing.

Dry run with a real Safe (not yet tried inside the real Safe interface; `test:chain` proves the server side against a real Safe 1.4.1 on a fork):
1. Run `dev`, sign in as an Owner, and use "Link a wallet" with the Safe's address and its chain (Ethereum, OP Mainnet, Base or Arbitrum One). Copy the signing link.
2. In the Safe interface (https://app.safe.global), open the Safe, then Apps, "My custom apps", "Add custom app", and enter `http://127.0.0.1:8787/sign/`. The interface reads `manifest.json` from there.
3. Open the app and paste the request code (the whole link works) into the box. Compare the action, site, organisation id, chain, wallet and expiry with the console.
4. Press "Sign with this Safe". Offchain: each owner signs the message in the Safe interface, with this window left open, and the page posts the result by itself. If the Safe is set to sign onchain: execute the transaction, then press "Check again".
5. Back in the console the wallet shows as "Safe 2 of 3" (or its own numbers), pending or linked. Set it as the recovery wallet and read "Recovery readiness" 72 hours later, or see amber "in force from" at once.

4. Before it works for real, the owner must: (a) deploy the indexer change (`apps/rebate-indexer`: `src/business.ts`, `src/api.ts`, `src/partnerFees/report.ts`, `src/partnerFees/split.ts`, `src/partnerFees/payout.ts`), the version whose answer holds `traders` with `unknown` and `breakdown` (the daily series, by chain, by fee token, the payouts; 2026-11-14): this console needs that version, and with an older indexer every partner reads "The figures are not available right now", the fees included; and set `BUSINESS_API_TOKEN` there, 32 characters or more, different from `REBATE_INDEXER_ADMIN_TOKEN`; it reads every partner's fee dashboard, so treat it as that kind of secret; (b) on the console set the variable `INDEXER_URL` (https) and the secret `INDEXER_TOKEN` (the same value, with `wrangler secret put`, never in the repository); (c) tell each partner that its figures are read by the fee recipient address of its integration, so a linked wallet included in reporting must be that recipient: another included wallet shows zero fees; (d) put that token in the host environment of the indexer's deploy: its `docker-compose.yml` passes `BUSINESS_API_TOKEN` to the process; (e) for each partner wallet that is a contract (a Safe), put its address and chain in the indexer's `CONTRACT_WALLET_AUTH_CHAINS`, as the existing partner dashboard needs: until then that wallet reads "The figures of this wallet are not shown"

An operator can exclude a linked address from partner reporting with `operator reporting <organisation id> exclude --wallet <address> --production`; `include` restores it. The preference applies across chains and later relinks. It affects the partner Overview and its CSV exports only; the wallet stays linked, with its recovery role, sanctions checks and trading authority. Each change is in the audit log.

## Screening, step by step, for the operator
Company registration checks the legal name, first Owner, additional named people and declaration signer against the official EU, UN and OFAC SDN exports. The operator dashboard refreshes the check when a review opens and the server repeats it on approval. Review the listed aliases and reference numbers, compare the declaration signer, and record why any possible matches are different identities before approving. Older applications require the operator to enter the handwritten signer once per review. Unreadable names, missing files or an index over 48 hours old leave approval unavailable. The applicant can still register.

The daily business-console workflow builds a sharded index of public names and aliases after tests and publishes it with the Worker. Screening uses only Ophis's own assets. It compares normalized names, including accents, punctuation, reordered words and common company suffixes. Apply migration 0030 before deployment. For a local review, run `pnpm build && node scripts/build-name-index.mjs`, then `pnpm exec wrangler dev`. A fresh Vite build clears the index. The CLI can use `operator names <id> [--signatory <name>]` and pass the reviewed `--revision` to `decide`, with `--resolution` for a false positive. The decision stores both the automatic results and the operator's disposition.

For periodic reviews of **existing approved organisations**, the offline procedure follows.

Every `operator ...` below is run from this app folder, with `dev` running, as `npx -y pnpm@10.34.9 operator ...`; in production, with `--production` at the end ("The operator's address in production").
1. Download the lists first, onto the operator's machine, in a text format (XML or CSV, not a PDF or a zip: `addresses` reads text), and keep each file as downloaded (the record names its SHA-256): the EU consolidated financial sanctions list (code `eu`, in every screening; the Commission's overview of sanctions resources: https://finance.ec.europa.eu/eu-and-world/sanctions-restrictive-measures/overview-sanctions-and-related-resources_en ), the UN Security Council consolidated list (code `un`; https://main.un.org/securitycouncil/en/content/un-sc-consolidated-list ) and the OFAC SDN list (code `ofac`; OFAC's Sanctions List Service: https://ofac.treasury.gov/sanctions-list-service ).
2. Search them OFFLINE, in the downloaded files, never in a web form: a name typed into a web form is sent to that site. Search for the legal name of the organisation, its first Owner, the other people the application named, and the signatory of the declaration (the sealed declaration: `operator get <item id> --reason periodic_review --out item.age`, opened offline, "Sealed declaration" above). What is found stays offline with the operator: no name and no detail is given to the command. The answer is `clear` when no entry resembles a name searched; `review` when an entry resembles one and it is not ruled out yet (the organisation is frozen while it is checked); `hit` when an entry matches.
3. Record the result. With the approval of a new organisation: `operator decide <id> approve ... --screening clear --list eu=<file> [--list un=<file>] [--list ofac=<file>]` (for `more` and `refuse` the two options are optional). Later, at each review: `operator screen <id> --outcome clear|review|hit --list eu=<file> [--list un=<file>] [--list ofac=<file>] --next-review YYYY-MM-DD`. The command reads each file on this machine and sends only its SHA-256. The next review is a real day, after today and at most 5 years ahead. `--tier` and `--source` are for an organisation with no record yet (a local seed). The command itself refuses, before anything is sent: `screen` with no `--list eu=<file>` or with another outcome, and `decide` with `--list` but no `--screening`.
4. What the command does on `review` and `hit`: an approval is refused; a screening of an active organisation freezes it in the same step (every session ends, and a member who signs in sees "This organisation is frozen", which does not say why). `operator unfreeze <id>` is refused until a screening that says `clear` is recorded: `screen ... --outcome clear` (the organisation stays frozen), then `unfreeze`.
5. Wallet addresses: `operator addresses ofac=<file>` takes every address (0x and 40 hex characters) from a list file and loads them in place of that list's earlier ones (1 to 1,000; a file with none is refused before anything is sent). When the file is an official SDN.XML the command also sends its publish day, which the console keeps (step 4 of the next section). It prints each organisation that holds a live wallet on any loaded list (linked, waiting for its second person, or named by an application that is not yet verified), and an active one is frozen; `unfreeze` is refused while such a wallet is live. A link request that was rejected, cancelled or has expired counts for nothing. A listed address cannot be linked: a member whose wallet proves such an address is refused, the attempt is a row in the organisation's audit log, the refused proof is kept and cannot be used a second time, and an active organisation is frozen at once; for an application the refusal is recorded once per address and the organisation is not frozen. Run the command again after each download of a list that names addresses. If it answers "The list may be loaded. Run the same command again.", do that: the list is in, and the freezes did not finish. A list cannot be emptied: a wrong load is corrected by loading the right file, and a local database is reset by deleting `.wrangler/state`.
6. The calendar is a manual chore: `operator list` prints "Reviews due, and frozen organisations": the organisations with no screening, or whose next review is passed or within 14 days, and every frozen one, which ends with what froze it: "frozen by <action> (<detail>) on <day>" (`organisation.freeze`: the operator; `kyb.screen (review)` or `(hit)`; `screening.wallet (0x...)`: a load; `screening.attempt (0x...)`: a member proved a listed wallet). A clear screening recorded later does not hide it. Under an organisation under review it prints "WARNING listed wallet refused: 0x..." when a wallet the application named was refused. Each `screen` sets the next date.
7. What the client sees, under Compliance, "Sanctions screening": the date, the lists, "Result: no match", the list version and the next review, and its linked wallets against the loaded address lists. Only a result of "no match" is ever shown to a client.
This is the procedure this build supports; whether it is enough is a question for the lawyer.
To try it locally, with `dev` running: `npx -y pnpm@10.34.9 operator addresses ofac=tests/fixtures/sanctions-addresses.txt`, then `npx -y pnpm@10.34.9 operator list` and `npx -y pnpm@10.34.9 operator screen <id> --outcome clear --list eu=tests/fixtures/sanctions-eu.txt --next-review 2027-11-13 --tier standard --source registry`. The files in `tests/fixtures/` are test data: invented names and addresses, no entry of any real list.

## The bot check of /recover (Turnstile)
The two anonymous recovery forms (start a recovery, cancel one) need a solved Cloudflare Turnstile check: each intent then costs one, which bounds anonymous recovery traffic. The server checks the token with Cloudflare, with this host's name and the action `recover`, and refuses on any doubt (`human_check_failed`). Only `/recover` loads the check's script; its policy adds only the check's origin and keeps Trusted Types.
1. Production: a widget in the Cloudflare dashboard (Turnstile, hostname `pro.ophis.fi`, Managed). Its public site key is in `TURNSTILE` (`src/server/index.ts`). Its secret goes to the Worker, typed at wrangler's hidden prompt, never in a command or a chat: `cd <this folder> && npx -y pnpm@10.34.9 exec wrangler secret put TURNSTILE_SECRET --env production`. A secret that was ever pasted elsewhere is rotated first (the widget, Settings, Rotate Secret Key; the old one keeps working for two hours). Free plan. ## The operator's address in production
The operator's API answers on `operator.ophis.fi`, behind Cloudflare Access (Zero Trust, Free plan). The operator signs in with their Cloudflare account: the login method "Cloudflare", restricted to the account's members; no email, no Google or Microsoft sign-in. The console then checks Access's signed proof itself, and after it the operator's token, as locally. Without the proof every request gets 403 `access_required`: the token alone does nothing, and neither does a proof alone. The order of the steps does not matter: until all are done, the address refuses everything.
1. Cloudflare dashboard, Zero Trust. If the account has no Zero Trust team yet, Cloudflare asks for a team name and, even for the Free plan, a card; it charges nothing. Integrations, Identity providers, Add new identity provider, Cloudflare: turn on "Restrict to account members". Then Access controls, Applications, Create new application, Self-hosted and private, Add public hostname: subdomain `operator`, domain `ophis.fi`, and no other row (an empty private hostname or IP row makes Create fail with "use_clientless_isolation_app_launcher_url can only be enabled for apps with private destinations", whatever "Allow clientless access" says). Access policies, Create new policy: Allow, Include, Emails: the operator's email. Login methods: Cloudflare only, with "Apply instant authentication".
2. `ACCESS_TEAM` and `ACCESS_AUD` (`wrangler.jsonc`, `env.production`) hold the team's domain (`<team>.cloudflareaccess.com`, without `https://`) and the application's AUD tag (the application, Edit, Additional settings). Both are public. A renamed team or a recreated application changes them: until they match again, the address refuses every request.
3. The token, once, on the operator's Mac, with wrangler logged in: `cd <this folder> && npx -y pnpm@10.34.9 operator token --production`. It makes a new token and puts it into the Keychain (item `ophis-operator-token`) and into the Worker's secret `OPERATOR_TOKEN`. It goes to both on stdin only, never as an argument (any process of the Mac can read those), and is never shown. Run it again to change the token. Before the first deploy, wrangler creates an empty Worker of that name to hold the secret; the deploy replaces its code and keeps the secret.
4. Then each command with `--production` at the end, from this folder: `npx -y pnpm@10.34.9 operator list --production`. The first time, and when the Access session ends, a browser opens the Cloudflare sign-in (it needs cloudflared: `brew install cloudflared`). The command never sends the token anywhere else: the address is fixed in it.

## The OFAC list file (M10)
The console can read the OFAC list by itself, once a day. Loading by hand (`operator addresses`, above) stays the fallback and the override.
1. The maker: `node scripts/ofac-list.mjs --out ofac.json` downloads OFAC's SDN.XML (about 30 MB) and writes one small file: the wallet addresses in it (every 0x and 40 hex characters, the rule of `operator addresses`), the day it was published, `made` (the time it ran, UTC, to the second) and the SHA-256 of the XML. `--from SDN.XML` reads a file already downloaded. It refuses, and writes nothing, for a file that is not the list, that is cut (no `</sdnList>` at the end), has no publish date or more than one, a `Record_Count` that is not its number of entries, or no address. The maker runs outside the console: the console reads only the file it writes. It was not run against OFAC's address from this build (no network here): try it once before relying on it.
2. In production the list is loaded by hand once a month (owner, 2026-11-15): download OFAC's SDN.XML from `https://sanctionslistservice.ofac.treas.gov/api/PublicationPreview/exports/SDN.XML` and run `operator addresses ofac=<SDN.XML> --production` ("The operator's address in production", above): until the first load the production desk sends no order. `SANCTIONS_URL` stays unset. The list is then current for 35 days after that load: past that, or if none was loaded, the operator sees it stale and the desk sends no order. A wallet OFAC adds between two loads passes the screen until the next one. The file reader below stays, for an owner who sets `SANCTIONS_URL` one day.
3. The console: the variable `SANCTIONS_URL` (https; empty: no file is read; set to an address the console does not take, such as http or one with a query: every read is "not readable", so the line turns stale once its last good read is 3 days old, at once if there was none). Once a day (a cron of the Worker) and on `operator sync` it reads the file: one request, 5 seconds, 2 MB, every field checked. The answer is one of: loaded (and it freezes as a load by hand does); the same file (the same SHA-256 and the same addresses: the list does not change); not readable (the lists do not change); held. Whatever the file gives (none set, not readable, the same, held), an organisation whose freeze failed after an earlier load, or that a load left for later (5 are frozen a run), is frozen now, and `operator sync` prints it. A freeze by the list file is recorded as the system's, a load by hand as the operator's.
4. Held: the file was read and NOT loaded, and `operator list` says why with a WARNING. `older`: it differs from the loaded list and is not newer: its publish day is the same or earlier. Only a strictly newer file replaces a list. `shrunk`: it lacks an address of the loaded list. Every removal waits for a person, since a removal makes the screen looser. A hold whose file had new addresses stops the desk and stays until a load, whatever the files read after it. `grown`: its new addresses are over a fifth of the loaded list. Counts alone decide nothing: the same count with other addresses is held too. `manual`: the loaded list was loaded by hand from a file with no publish date, and the list file never replaces such a list. To end it: compare the file, then load the official SDN.XML by hand (`operator addresses ofac=SDN.XML`: the command sends its publish day, so the daily read never rolls that load back). Do not load the maker's JSON by hand: it gives a list with no day, which then holds every read as `manual`. A load by hand is never held and clears what is held.
5. Stale: `operator list` prints one line per loaded list, with the day the file was made, and a WARNING when the address is set and the last good read is missing or 3 days old, or the file read was made 3 days ago or more. So a maker that stops while the file is still served is seen on the fourth day. A feed that stops must be seen: look at `operator list` as part of the routine, since no alert is sent. In production with no file set, the line is stale when no list was loaded by hand, or the last load is 35 days old. While it is stale, or a held file has addresses the loaded list lacks, the desk sends no order (the signing page says the list is not up to date); with a file set, loading the list by hand lifts that until the next read of the file, for 3 days at most; with no file, a load by hand keeps the list current for 35 days. A hold ends with a load: by hand, or of a later file the rules take; a hold whose file added nothing also ends with a read of the loaded list again. A hold that keeps coming back needs a load by hand, so the operator's address in production (above) must be set up before the desk goes live.
6. Locally: `seed` adds `SANCTIONS_URL` for the stand-in that `dev` starts (`scripts/list-stub.mjs`, port 8794: the list the maker builds from `tests/fixtures/sdn-test.xml`, the real structure with invented values). `operator sync` loads it. Other cases: open `http://127.0.0.1:8794/stub/shrunk` (or `grown`, `older`, `shape`, `down`, `ok`), then `operator sync` and `operator list`.
Not in this build: an alert (Telegram), other readers of the list (the Railgun pool, the payouts, the swap backend), EU or UN address lists as files, a signature on the file.
