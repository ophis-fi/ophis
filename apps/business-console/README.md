# Ophis Business console

Local only for now: passkey sign-in, enrolment of members (by company sign-in at Microsoft or Google, or by three words), roles with two-person approval and the audit log, wallets with the recovery wallet, last-Owner recovery, Support, and registration by invitation with the operator's review. Design, schema, routes and invariants: `ARCHITECTURE.md`.
Never deploy from a laptop, and never run a remote wrangler command from here.

Needs Node 22.18 or later and Google Chrome. Run everything from this folder, with pnpm as `npx -y pnpm@10.34.9`.

```sh
npx -y pnpm@10.34.9 install --ignore-workspace   # the flag is required: without it pnpm installs the root workspace
npx -y pnpm@10.34.9 migrate     # creates or updates the local D1 database (.wrangler/); run it again after pulling (now up to 0011). If it fails with "duplicate column name" (0005_onboarding.sql was renamed 0006): stop dev, delete .wrangler/state, migrate and seed again
npx -y pnpm@10.34.9 seed        # one organisation (domain northwind.example, company sign-in "none"), one Owner seat; prints a one-time enrolment link (10 minutes). Add: -- --company microsoft (or google) for an organisation that uses the company sign-in
npx -y pnpm@10.34.9 dev         # builds the console and the signing page, and serves both with the Worker: console http://localhost:8787, signing page http://127.0.0.1:8787/sign/. Also starts the local stand-ins: two DNS resolvers (8790, 8791), the Microsoft and Google sign-in (8792) and the rebate indexer (8793)
npx -y pnpm@10.34.9 seed -- --demo   # demo mode, LOCAL ENVIRONMENT ONLY: the organisation is an institution with one linked wallet named "Demo wallet" (no signature proved it; the command refuses any environment but "local"), so one person can try the order ticket
npx -y pnpm@10.34.9 seed -- --live   # partner figures, LOCAL ENVIRONMENT ONLY: the organisation is a partner with one linked "Demo wallet" at the partner address of the indexer's contract file, so Overview shows the stand-in's figures
npx -y pnpm@10.34.9 activate    # first Owner only: local stand-in for the activation by the recovery wallet (milestone 5)
npx -y pnpm@10.34.9 skip        # local stand-in for the passing of time: every wait that runs is over (recovery wallet 72 h, recovery request, 24 h after a cancel)
npx -y pnpm@10.34.9 dns <name> <value>   # milestone 5: publishes a TXT record in the two local stub resolvers that "dev" starts (ports 8790 and 8791)
npx -y pnpm@10.34.9 operator list        # milestone 5: the operator's command (also: invite, decide, freeze, unfreeze, items, get); needs "dev" running
```

`seed` writes `.dev.vars` when it is missing and adds what it lacks (the challenge key, the operator's token, two client secrets for the local stand-in, and `INDEXER_URL` with `INDEXER_TOKEN` for the local stand-in of the rebate indexer). It is git-ignored: never commit or print it.

## A tester gets in, step by step
Everything starts at http://localhost:8787 (the console). Use Chrome. Each person needs a security key of their own, or a Chrome virtual authenticator per browser profile (DevTools, More tools, WebAuthn: ctap2, usb, resident keys, user verification).
1. Once: `install`, `migrate`, then `seed -- --company microsoft` (or plain `seed` for the three-word path). Keep the link it prints (10 minutes).
2. `dev`, and leave it running. Open http://localhost:8787 : the sign-in page, with the footer line.
3. Open the printed link. Create the passkey. In a second terminal run `activate` (it stands in for the first Owner's activation). Go to http://localhost:8787 and press "Sign in with a passkey".
4. Organisation, My passkeys, "Add a passkey" (a second key): an Owner can do nothing else before.
5. "Invite member": a name, a role and, with the company sign-in, a work email at the domain `seed` printed (`northwind.example` for the first organisation; any local part). Copy the link.
6. In another browser profile open the link. Press "Continue with Microsoft": the browser goes to the local stand-in (`http://127.0.0.1:8792`, "Test only"), where you type the address to sign in as. Type the invited address. Back on the console, "Create passkey". No words appear. The passkey can only be created in the browser that signed in: the same link opened in a third browser asks for the company account again. (Type another address to see the refusal; `someone@outlook.com` to see a personal account refused.)
7. Back as the Owner: reload, "Waiting for confirmation" shows the address "confirmed by Microsoft" and the key type. "Approve with passkey". A key role needs a second key-role member too, or waits 72 hours if there is none (`activate` stands in for that wait).
8. The new member signs in at http://localhost:8787 with the passkey. The company account is not asked again.
9. Without `--company`: the member's page shows three words, which the member sends to the inviter over a channel they trust, and the inviter types them.
10. A new organisation from scratch (registration): `operator invite` prints an application code; open http://localhost:8787/apply and follow "Onboarding" below. Its Onboarding page has the step "Company sign-in", where the first Owner signs in at the stand-in with an address at the organisation's own domain.
Microsoft and Google themselves are not reachable from this build: only the stand-in is. What the owner must set up for the real ones is in the last section.

Then, in the app (each person needs their own security key, or a Chrome virtual authenticator per browser profile):
1. Organisation, My passkeys, "Add a passkey". An Owner needs two hardware keys before anything else works.
2. "Invite member" gives a one-time link. Three-word path (company sign-in "none"): 10 minutes for key roles, 24 hours for Trader and Viewer; the member opens it on their own device, creates a passkey and sends three words to the inviter over a channel both trust. Company sign-in: 24 hours for every role; the member signs in with the company account, then creates the passkey.
3. Under "Waiting for confirmation" the inviter types the words, or approves what the provider confirmed, and confirms with a passkey. Key roles need a second key-role member too. Only an organisation that has had no other key-role member in the last 30 days waits 72 hours instead (locally, `activate` stands in for that wait).
4. "Re-enrol" does the same for a member who lost every passkey. The old passkeys are suspended: for 24 or 72 hours one of them can still sign in to a page with one action, "Stop this replacement".
5. A stop freezes the seat. An Owner or Admin can also freeze a seat at once: Members and roles, "Manage", "Freeze seat". A frozen member who signs in sees who froze the seat and when; a replaced passkey can still stop its replacement on a frozen seat. A member's last passkey is never revoked.
6. Unfreezing a seat, removing a member, changing a role and changing the passkey rule for key roles take two people: one asks ("Manage", or the passkey rule section), a different member with a key role approves under "Approvals" after a passkey check. Each button is preceded by what it will do.
7. Compliance (Owner, Compliance officer, Viewer): the audit log in plain words with both hashes per row, "Chain verified" computed by the server, and "Export CSV".
8. Two passkeys of one seat need different names. If the local database already holds two with the same name, `migrate` fails: delete `.wrangler/` and seed again.
9. Wallets (Organisation, Wallets): an Owner or Admin uses "Link a wallet" and gets a signing link, valid 7 days. Nothing is stored yet. The link opens the signing page on its own address (`http://127.0.0.1:8787/sign/` locally), in the browser that holds the wallet. The wallet signs one typed message that names the organisation. A wallet with one key, or a custodian's browser extension, signs through the browser. A Safe signs inside the Safe interface (below).
10. With colleagues in key roles the link then waits under "Approvals" for a different member. An organisation with a single key-role member links at once. "Manage" on a wallet: "Unlink" (one person; never the recovery wallet), "Set as recovery wallet" (an Owner asks, a second person approves, in force 72 hours later), "Cancel change" (any Owner, during the 72 hours).
11. Security and data, for an Owner: "Recovery readiness" says Ready, At risk with the next step, or Not recoverable. A Safe that is the recovery wallet is read on the chain at that moment: green needs a genuine Safe (official proxy code, singleton and fallback handler), a threshold of 2 or more, no module, and the owners it had when it was approved. A contract that only answers like a Safe is stored as a single key. Below it: the recovery sheet, with "Print the recovery sheet".
12. Last-Owner recovery, when no Owner can sign in. Open http://localhost:8787/recover (no sign-in), enter the organisation id from the recovery sheet and create a passkey on a new security key. The page shows three words and a signing link. The signers of the recovery wallet open the link on the signing page, compare the organisation id and the three words, and sign. Then the request waits 72 hours (`skip` locally). Every member sees a banner at sign-in: an Owner can cancel after a passkey check, an Admin, Approver or Compliance officer can add 72 hours once, and the recovery wallet can cancel by signing (the form on /recover, with the request number from the banner). After the wait, "Continue with the new passkey" on /recover makes the requester an Owner. For 7 days the organisation is in quarantine and a replaced Owner passkey, used at sign-in, can stop the recovery. The next request can start 24 hours after a cancel, and not while a completed recovery can still be stopped (7 days, or until it is stopped).
13. An override ("Override the Owners" on /recover) works only for a green recovery wallet, within 30 days of an Owner cancelling or stopping a recovery. No Owner can cancel or stop it.

Dry run with a real Safe (not yet tried inside the real Safe interface; `test:chain` proves the server side against a real Safe 1.4.1 on a fork):
1. Run `dev`, sign in as an Owner with two keys, and use "Link a wallet" with the Safe's address and its chain (Ethereum, OP Mainnet, Base or Arbitrum One). Copy the signing link.
2. In the Safe interface (https://app.safe.global), open the Safe, then Apps, "My custom apps", "Add custom app", and enter `http://127.0.0.1:8787/sign/`. The interface reads `manifest.json` from there.
3. Open the app and paste the request code (the whole link works) into the box. Compare the action, site, organisation id, chain, wallet and expiry with the console.
4. Press "Sign with this Safe". Offchain: each owner signs the message in the Safe interface, with this window left open, and the page posts the result by itself. If the Safe is set to sign onchain: execute the transaction, then press "Check again".
5. Back in the console the wallet shows as "Safe 2 of 3" (or its own numbers), pending or linked. Set it as the recovery wallet and read "Recovery readiness" 72 hours later, or see amber "in force from" at once.

Test: `npx -y pnpm@10.34.9 test` (builds, then the invariant tests in the Workers runtime, with a stubbed JSON-RPC for the two endpoints and real signatures from the public anvil test keys), `npx -y pnpm@10.34.9 typecheck`,

`npx -y pnpm@10.34.9 test:e2e` (headless Chrome, one browser context per person with a virtual authenticator each; needs port 8787 free; screenshots in `.shots/`).

Support (milestone 6): the rail entry and the top button open `#/support`. The Worker needs the secret `TYPESAFE_API_KEY`: add the line `TYPESAFE_API_KEY=...` to `.dev.vars` (git-ignored; never commit or print it). Without it every question gets the hand-over card.
`npx -y pnpm@10.34.9 test:jev` (on demand, needs the network and `TYPESAFE_API_KEY` in the environment): sends the 32 questions of the prototype through the server's own functions and prints each outcome, the accuracy and the median latency, never the key.
`test:e2e` includes the Support flow; with the key in `.dev.vars` that part needs the network too.

Onboarding (milestone 5a). Run `migrate` again, and `seed` once: it adds `OPERATOR_TOKEN` to `.dev.vars` (never printed). `seed` and `activate` still work as before, for an organisation that is active at once.
0. Applications are by invitation: `npx -y pnpm@10.34.9 operator invite` prints an application code (one use, 14 days).
1. Open http://localhost:8787/apply (no sign-in). Enter the application code, the company, its email domain and a work email at that domain, then create the passkey on a hardware key. Nothing is stored. The page shows one TXT record, `_ophis-verify.<domain>` with the value `ophis-verify=<code>`, and a link to come back (7 days).
2. Publish the record: locally `npx -y pnpm@10.34.9 dns _ophis-verify.<domain> ophis-verify=<code>`. Press "Check DNS". Both resolvers must show the exact value. Then the organisation exists, not yet verified, and you sign in with that passkey.
3. Onboarding (the rail entry): add the second passkey under Organisation, choose the company sign-in (Microsoft, Google, or none: with a provider you sign in once with your own company account, locally at the stand-in, with an address at the domain you proved), then name the recovery wallet. The wallet signs "Activate this organisation and confirm its first Owner passkey" on the signing page, after its holders compared the three words. Or invite a second Owner, who needs two passkeys. Then the step "Declaration" (below), then "Submit for review". A recovery wallet with a single key is accepted only while you are the only member. Any change to the Owner seats, their passkeys or the named wallet after that puts the organisation back to "Not submitted".
4. The operator: `npx -y pnpm@10.34.9 operator list` shows what to compare (domain, the first Owner's three words and passkey hash, the recovery wallet, its kind and colour, the sealed declaration's size, date and SHA-256) and the name of the submission: an approval carries it, so that a change followed by a new "Submit" is never approved unseen. Then one of
   `operator decide <id> approve --submission <the 16 characters "list" printed> --tier standard --source registry --evidence "<reference>" --sha256 <64 hex> --next-review 2027-11-11`,
   `operator decide <id> more --reason details_differ --tier standard --source registry`, `operator decide <id> refuse --reason not_eligible --tier standard --source registry`,
   `operator freeze <id>` (it ends every session of the organisation; a member who signs in sees "This organisation is frozen"), `operator unfreeze <id>`. Each is a row in the client's own audit log. The operator's API answers on `operator.localhost:8787` only, and only locally.
5. After the approval the organisation is active, the recovery wallet is in force at once, and Compliance shows the "KYB record" block. The one document stored is the sealed declaration.

Sealed declaration (milestone 5b). Run `migrate` and `seed` again: `seed` makes a local TEST key for sealing. Its identity (the secret half) is `.dev.seal-identity`, next to `.dev.vars`, git-ignored, never printed; its recipient (the public half) goes into `.dev.vars` and `.env.local`, and the build compiles it into the console. Every other environment has no recipient yet: the page says "Sealing is not configured" and an upload answers `not_configured`.
1. Onboarding, step "Declaration": "Print the declaration" gives one page with the values the server holds (the page cannot edit them). A person who may bind the company signs it.
2. Choose the scan (PDF, PNG or JPEG, 10 MB at most) and press "Seal and upload". The file is encrypted in the browser, in the age v1 format (`age-encryption` 0.3.1, post-quantum hybrid recipient `age1pq1...`), to the key shown as "Sealed to key ...". The Worker stores the sealed file in the bucket `SEALED` (R2, simulated locally) under a random name, with a row of what it knows: size, its own SHA-256 of the sealed file, the key. It holds no key and never sees the clear file. A new upload replaces the old one and puts the organisation back to "Not submitted". "Submit for review" needs it.
3. The operator: `npx -y pnpm@10.34.9 operator items <organisation id>` lists the sealed items; `operator get <item id> --reason kyb_review --out item.age` writes the file, still sealed, and refuses before it asks when the file exists or the id is not 32 hex characters (reasons: `kyb_review`, `periodic_review`, `authority_request`, `client_request`, `incident`). Every download is a row in the client's own audit log, with the reason. No route returns clear text.
4. Opening it is offline, with age 1.3 or later (the first release with `age1pq1` keys), and is not logged. First `shasum -a 256 item.age`: it must equal the SHA-256 of the audit row.
   Local test key: `age -d -i .dev.seal-identity -o declaration.pdf item.age`. Not run on this machine (the `age` binary is not installed here): `test:e2e` opens the downloaded file with the same identity through the library, in Node, and compares it with the original.
   A real key (none exists yet; `key-custody.md` section 4): on the separate offline account, with one of the two hardware keys, `age -d -i yk-A.txt seal-identity-g1.age | age -d -i - -o /Volumes/ram/item.pdf item.age`. The output goes to a RAM disk and is deleted after use. Treat the opened file as a file from a stranger.

`npx -y pnpm@10.34.9 test:dns` (on demand, needs the network): asks Cloudflare and Google, over DNS-over-HTTPS, for the TXT record of example.com through the server's own lookup and parser, and prints both answers.
`test:e2e` also needs ports 8790, 8791, 8792 and 8793 free. If port 8787 is taken (your own `dev`), run it as `E2E_PORT=8797 npx -y pnpm@10.34.9 test:e2e`: the browser still uses the address http://localhost:8787. Overview and Desk of an institution (demo mode). No order is sent, signed or executed, and the figures are examples; the two-person control, the roles and the audit log are real. To try an order locally with two members:
1. `npx -y pnpm@10.34.9 seed -- --demo` (local environment only): an institution with one linked wallet named "Demo wallet". Open the printed link, create the passkey, run `activate`, sign in: you land on Overview. A plain `seed` gives a partner: its Overview is live (below), and its Desk says "The desk is for institutions."
2. Under Organisation add your second passkey, then "Invite member": an Approver (a Compliance officer, an Admin or a second Owner works too). Open that link in another browser profile, create the passkey, type the three words as the Owner, then run `activate` once more: it stands in for the 72 hour wait of a first key-role colleague. The new member signs in and adds a second passkey.
3. As the Owner (or as a Trader you invite the same way): Desk, fill the ticket, "Review order" (the estimate is the server's; nothing is signed), "Send for approval" (it asks for your passkey when the last check is older than 5 minutes; `node scripts/dev.mjs stale` makes every check that old). A limit price must lie within 20% of the reference price: the ticket shows the range. The wallet must be linked on the chain of the order. The preparer can cancel it, in the blotter or under Approvals.
4. As the second member: Organisation, Approvals, "Review", then "Approve" (a passkey check) or "Reject". The blotter then says "Approved. Not sent: demo" or "Refused", and the record of the order shows who prepared and who decided it. Every step is a row of the audit log (Compliance).
5. Every "Export CSV" button downloads a file the server built: its name starts with `ophis-demo-` and each row ends with `source` = `demo`.

## Before real Microsoft and Google accounts work
Nothing here has ever called Microsoft or Google: `src/server/oidc.ts` holds their addresses as constants (`REAL_ENDPOINTS`) for an environment that does not exist yet. The owner must:
1. Choose the production hostname of the console (it is also the passkey relying-party id, and final). The redirect address is `https://<that hostname>/api/company/callback`.
2. Microsoft Entra: register an application, "Accounts in any organizational directory" (multitenant, no personal accounts), platform Web, that redirect address. Token configuration: add the optional ID token claims `email`, `xms_edov` and `acct` (0 member, 1 guest: a guest, or a token without the claim, is refused). Create a client secret. Note the application (client) id.
3. Google Cloud: an OAuth client of type "Web application" with that redirect address, and the consent screen (scopes `openid` and `email`; user type External, published). Note the client id and the client secret.
4. Add the environment to `ENVIRONMENTS` (`passkeys.ts`) and to `IDPS` (`oidc.ts`: `REAL_ENDPOINTS` plus the two client ids), and set the Worker secrets `MICROSOFT_CLIENT_SECRET` and `GOOGLE_CLIENT_SECRET` with `wrangler secret put` (never in the repository).
5. Then try one real sign-in of each provider before anyone relies on it: the code expects `xms_edov` as the boolean `true`, `acct` as `0`, and Google's `hd` for a Workspace account, as documented, and has not seen a real token.
